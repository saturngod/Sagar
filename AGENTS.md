# AGENTS.md — EPUB Translation Studio

> Instructions for coding agents and contributors. Apply these rules before modifying this repository.
> If a task conflicts with this document, explain the conflict and prefer the smallest safe change.

## 1. Product mission

Build an **offline-first desktop EPUB Translation Studio**. A user imports a DRM-free, reflowable EPUB, reads the original chapter on the left, manually translates it on the right, saves progress locally, and exports a **translated EPUB** that preserves the source book's structure and non-translated assets.

**Phase 1 is manual translation only.** Do **not** integrate LLMs, AI translation services, cloud accounts, sign-in, telemetry, subscription/billing, or mobile support unless explicitly requested later. Design boundaries so an AI translation service can be added without restructuring import, persistence, or export.

Target systems: **Windows, macOS, Linux**.

## 2. Confirmed stack

- **Desktop shell:** Tauri 2.x.
- **Frontend:** React + TypeScript (Vite, as generated by the Tauri React/TS template).
- **Package manager:** **Bun** exclusively for JS dependencies/scripts. Do not introduce npm, pnpm, or Yarn lockfiles.
- **Backend / EPUB engine:** Rust (inside `src-tauri` initially; extract into a crate when complexity warrants).
- **Project database:** SQLite, accessed through a Rust-owned repository/service layer (e.g. `rusqlite`). Do not have frontend components issue raw SQL.
- **Reader:** EPUB.js or a safe XHTML rendering adapter, to be decided by a documented prototype. Render imported book content as **untrusted**.
- **Translation editor:** Tiptap/ProseMirror with a deliberately restricted schema, selected after a round-trip preservation spike. Never assume arbitrary EPUB XHTML survives a Tiptap parse/serialize cycle.
- **Styles:** Existing app styles; choose a styling library only if it demonstrably reduces complexity. Ensure Myanmar Unicode readability.
- **Validation:** Internal EPUB archive/manifest checks for the MVP; support optional EPUBCheck in the developer/test workflow for full conformance testing. Do not claim full EPUB conformance without it.

Use existing dependency versions and Tauri capabilities already present in the scaffold; do not blindly overwrite generated configuration.

## 3. User workflow and MVP boundaries

1. Open/import an `.epub` through the OS file chooser.
2. Parse the book and display its metadata and **reading-order** chapter list.
3. Select a chapter; show source content on the left and an editable translation on the right.
4. Translate supported text blocks manually; preserve the original XHTML and associated assets.
5. Autosave edits, restore the active chapter and draft on restart, and show chapter progress.
6. Review missing/incomplete blocks and export a separate `.epub` to a user-selected location.
7. Reopen the exported file and verify navigation, text, images, links, and metadata.

**Supported initial content:** non-DRM, reflowable, text-heavy EPUB 3 XHTML books. Add EPUB 2/NCX compatibility after the first EPUB 3 end-to-end milestone or as part of a tested compatibility task. Clearly report unsupported/fixed-layout/complex resources instead of silently degrading them.

**Non-goals for Phase 1:** OCR, PDF, MOBI, fixed-layout editing, DRM removal, collaborative editing, cloud sync, AI translation, automatic glossary generation, online dictionary, arbitrary XHTML source-code editing, and real-time cross-device sync.

## 4. Architecture boundaries

**React/TypeScript**
- Application shell, project list, chapter navigation, read-only preview, editable target blocks, completion indicators, export dialogs, and user feedback.
- Typed client-side API wrappers call Tauri commands. No direct source-EPUB filesystem mutation.
- UI state is ephemeral. Saved translation content in SQLite is authoritative.

**Rust application services**
- Validate imports; safely inspect ZIP/OCF, find package document, parse manifest/spine/nav, extract source resources.
- Create and manage projects, chapters and stable source-block IDs; persist translated fragments and statuses in SQLite.
- Rebuild a translated EPUB from an immutable source snapshot, preserving original resources unless explicitly changed.
- Manage temporary files, atomic export, path safety, and structured error messages.

**SQLite / project storage**
- Store project identity, original file hash, metadata, chapter/block mapping, translated fragments, progress, timestamps, and schema version.
- Keep a **private immutable copy** of the imported source EPUB, with references to its extracted resources, inside app-owned project storage.
- Keep all editable translations separately from source files. Export does not overwrite the source file.

**Future AI adapter (not implemented)**
- Could consume source block IDs plus text/context, propose translations, and save through the **same translation service** after user review.
- Must never bypass the editor's autosave/version rules or overwrite manually edited text without confirmation.

## 5. Invariants — never break these

1. **Source immutability:** importing, editing, and exporting never modify the user's original EPUB or its stored snapshot.
2. **Loss-aware editing:** no silent loss of `em`, `strong`, anchors/hrefs, IDs, footnotes, ruby, inline elements, images, semantics or meaningful whitespace. If a block cannot round-trip safely, mark it unsupported, preserve it, and warn before export.
3. **Stable identity:** distinguish `spine item`, XHTML resource, and UI chapter label. A TOC entry is not necessarily a single XHTML file. Persist block IDs created at import; don't use array indices as primary keys.
4. **Reading order:** derive sequence from OPF `spine`, not ZIP entry order or alphabetical filenames.
5. **Local durability:** changing chapters, restarting, or an interrupted write must not silently erase saved work; persist revisions transactionally with observable save state.
6. **Valid output:** preserve required OCF/package structure, resource paths and references; write `mimetype` first, uncompressed, with content `application/epub+zip`; update relevant OPF/nav metadata when appropriate; re-open exported EPUB as a smoke test.
7. **No partial misleading export:** incomplete/unsupported chapters produce a visible review summary; user must explicitly choose whether to export a draft. A "completed" export requires all required blocks to be reviewed or intentionally skipped.
8. **Offline and private by default:** no requests containing book content. Never include raw book text or filesystem paths in telemetry/logging.
9. **Cross-platform:** no hard-coded paths, shell commands, OS-specific separators, or assumptions about font shaping.
10. **Accessible UI:** keyboard navigation, visible focus, resizable panes, readable source/target typography, and correct Unicode handling (including Burmese combining marks).

## 6. Content processing rules

- EPUB is a ZIP-based publication format, not a plain text archive. Consult the EPUB specification before touching OCF, OPF, nav/NCX, XHTML, or relative URLs.
- Parse XML/XHTML with namespace-aware tools; **never** parse EPUB structure with regular expressions.
- Protect against ZIP slip/path traversal, absolute paths, symlinks, duplicate entries, archive bombs, unexpected file sizes, and malformed XML. Apply size/count limits with useful errors.
- Resolve paths relative to the containing document (not the book root by assumption); preserve URI fragments and query components where valid.
- Store the original XHTML/resource bytes (or faithful snapshot) and a separately normalized **editable block model**.
- Block segmentation must account for headings, paragraphs, list items, block quotes, and notes. Do not flatten a book to a plain string.
- Preserve non-edited assets byte-for-byte whenever possible. For translated blocks, emit valid escaped XHTML from an allowlisted editor schema.
- Sanitize/contain book HTML for preview. Do not execute embedded scripts or let EPUB content invoke privileged Tauri APIs. Disable or tightly control external/network resources.
- Treat EPUB.js preview and translation editor as separate concerns; display preview can differ from the export serialization source.
- Export to a new temporary archive, validate, then safely move it into place after confirming overwrite behavior.

## 7. Working conventions

### Suggested directory structure

```text
src/
  app/                # shell, routing, providers
  features/
    library/          # project/open-book experience
    chapters/         # list, navigation and status
    reader/           # read-only source rendering
    translator/       # translation editing/review
    export/           # export UI and validation feedback
  components/         # reusable accessible UI elements
  hooks/
  lib/tauri/          # typed command bridge and DTOs
  types/
src-tauri/
  src/
    commands/         # thin Tauri command adapters
    domain/           # project, chapter, block models
    epub/             # import, parse, resource map, export
    services/         # application use cases
    storage/          # SQLite repository/migrations
    security/          # archive/path/content checks
  migrations/         # if a migration tool is selected
tests/
  fixtures/           # small, licensed/synthetic EPUB files
```

Follow existing scaffold conventions if different. Do not create speculative directories and abstractions without a concrete feature.

### Coding standards

- TypeScript: strict mode, avoid `any`, meaningful types, small components and hooks, explicit loading/error/empty states.
- Rust: use `Result` for fallible operations; structured domain errors; no `unwrap()`/`expect()` on user data; keep Tauri commands thin.
- Validate runtime command inputs at the Rust boundary. Frontend types are not a security boundary.
- Keep business logic in services/modules, not JSX components or command handlers.
- No hidden side effects: file writes, DB changes and export must have an explicit service entry point.
- Keep one source of truth for the saved translation. Debounced autosave must flush before chapter switch and export.
- Keep commits/changes scoped; don't refactor unrelated code or introduce a web server for an offline desktop app.
- Add database migrations for schema changes; never silently drop a user's translation database.

### Professional UI/UX and consistency

These rules apply to every new or changed screen. Use the existing Sagar design
patterns and the latest confirmed user workflow. See `Design.md` for tokens,
shared components, CSS conventions and worked examples of these rules. They do not authorize features
outside the agreed product scope.

**Layout and hierarchy**
- Keep reading and writing as the main workspace activity. Use two persistent control rows by default: one book/chapter navigation header, then the pane headers. Show formatting and table tools only when requested or relevant.
- Group related actions; avoid duplicate chapter titles, stacked toolbars, repeated settings controls, and excessive padding. Keep primary actions visible and put secondary tools within a clearly labeled control.
- Support the configured minimum window size, pane resizing, and larger text without clipped controls or overlapping content. Keep a usable chapter picker when space is limited.
- Use consistent alignment, spacing, typography, borders, radii, and control heights from `src/styles/tokens.css` and existing shared styles. Extend a shared pattern instead of adding conflicting CSS overrides for individual screens.

**Controls and icons**
- Every button with visible text must pair its label with a relevant icon from the shared `Icon` component. Text-only buttons are not allowed; icon-only buttons are allowed with accessible names and tooltips. Apply this consistently to primary/secondary actions, tabs, pickers and list buttons. Use an X icon-only button for dialog-header dismissal, and use “Save” as the save action label (with “Saving…” while pending).
- Use the shared `Icon` component and `icon-button` pattern for compact toolbar actions. Default pane-header icon buttons are 34 × 34 px with 18 px icons; match sizes within each group. Avoid mixing text buttons with different heights or padding for equivalent toolbar actions.
- Use recognizable icons for Reader/Rich text, HTML, AI, formatting, paragraph (¶), review, and settings. Keep clear text labels for consequential primary actions such as Save and Export, and for form fields or ambiguous choices.
- Every icon-only button must have an action-specific accessible name and tooltip. Show selected views with `aria-pressed`, disclosures with `aria-expanded` and `aria-controls`, and a visible active style.
- Use an X icon in dialog headers, with an accessible Close label. Keep Escape, focus trapping, and focus restoration consistent. If closing cancels work, make that behavior clear in its label or tooltip.
- Make hover, focus, active, loading, and disabled states distinct. Disabled text must remain readable; do not combine faded backgrounds and low-contrast labels. Target at least 4.5:1 text contrast in both themes, including disabled text.

**Settings and forms**
- Put theme and reading text size in Settings → Appearance, with meaningful labels and a preview. Preserve existing keyboard shortcuts and saved preferences.
- Keep global settings separate from Book Settings. Expose the same Book Settings dialog from both the library row beside Trash and the workspace book header.
- Book Settings owns export metadata and book-wide instructions for explicitly authorized AI features. Explain what is saved, what export uses, and when instructions are sent. Keep current-run instructions separate and explain any effect on Retry.
- Use consistent field layouts, labels, validation messages, Save/Cancel placement, and observable save state. Preserve entered values after errors. Do not require opening a chapter to edit book-level preferences.

**Editor behavior and feedback**
- Place empty-editor hints outside text flow: the caret starts at the beginning, the hint remains on focus, and typing removes it. Placeholder text must never enter saved content.
- External draft updates, including an accepted AI result, must appear immediately in the mounted Rich editor. Do not require switching to HTML and back. Apply the same validation and loss-aware conversion checks to every update path.
- Do not reload editor content during normal typing or IME composition. Preserve caret, selection, undo history, and Myanmar combining marks. Ignore stale asynchronous results rather than replacing newer edits.
- Provide concise, actionable loading, empty, save, success, and error feedback. Explain validation failures without hiding the cause; retain recoverable output and input. Retry must clearly indicate whether it continues, revalidates, or restarts.
- Keep product language consistent: use “Sagar” for the app, “Book Settings” for per-book preferences, and chapter-based progress for the current chapter-authoring workflow. Avoid implementation jargon in user-facing messages.

**UI verification**
- Before reporting a UI change complete, check affected controls, focus order, keyboard actions, selected/disabled/error states, and light/dark appearance. For editor changes, check empty, typed, and externally updated content plus Myanmar text where possible.
- Inspect the rendered result at the normal and minimum supported window sizes when a current running build is available. A successful lint/build is not visual or interaction verification; explicitly report unverified native or cross-platform behavior.
- Keep UI changes scoped. Do not introduce a new styling framework or perform an unrelated redesign to satisfy a small consistency fix.

## 8. Definition of done for each feature

- [ ] Meets the acceptance criteria in `Plan.md`; handles cancel, invalid input, and I/O errors.
- [ ] User-visible state includes loading, success, errors, and save status where applicable.
- [ ] Unit tests for parsing/logic and integration test or fixture for any EPUB read/write change.
- [ ] No loss of source content; preserved links and assets remain usable.

- [ ] UI follows the shared layout/control patterns above; labels, focus and disabled states remain readable and usable.

## 9. Agent execution protocol

For each request:

1. Read `AGENTS.md`, then `Plan.md` and the relevant implementation files.
2. Pick the earliest unfinished milestone affected by the task.
3. State a short implementation plan and any assumptions before large edits.
4. Make the smallest end-to-end, testable slice (UI + service + persistence when necessary).
5. Add tests for new EPUB structures and regression fixtures for any reported bug.
6. Run available checks. Summarize changed files, test results, risks, and the **next unfinished task**.
7. Update `Plan.md` checkboxes only when the functionality exists **and** acceptance criteria are met. Never mark future work completed speculatively.

## 10. Decision log

- **ADR-001:** Tauri 2 + React/TypeScript + Bun is locked for desktop v1.
- **ADR-002:** Manual translation first. AI is a post-MVP feature behind a future service interface.
- **ADR-003:** Rust owns EPUB parsing, persistence boundaries and export; React owns rendering and editing UI.
- **ADR-004:** Source EPUB is immutable; translation data is a separate recoverable local project.
- **ADR-005:** First supported target is text-heavy, reflowable, DRM-free EPUB 3; unsupported features must be explicit.
